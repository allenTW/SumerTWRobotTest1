Claude Code 使用介紹

Anthropic 推出的命令列 AI 開發助手，讓 Claude 直接在你的終端機中讀取程式碼、編輯檔案、執行指令，協助完成軟體工程任務。

✍️ 作者：allenTW 🏷️ 版本：v1.3.0 🗓️ 最後更新：2026-09-17 📦 原始碼

什麼是 Claude Code？

Claude Code 是一個在終端機（CLI）中運作的 AI 程式設計代理人。它可以理解你整個專案的程式碼結構、 直接讀寫檔案、執行 shell 指令、操作 git，並依照你的指示完成除錯、重構、新增功能等任務。 除了 CLI，也提供桌面版、網頁版（claude.ai/code）以及 VS Code、JetBrains 的 IDE 擴充套件。

安裝方式

# 使用 npm 安裝
npm install -g @anthropic-ai/claude-code

# 安裝完成後，在專案資料夾中啟動
cd your-project
claude
💡 需要 Node.js 環境。安裝完成後首次執行會引導你登入 Anthropic 帳號完成授權。

核心功能

讀寫程式碼

直接瀏覽、搜尋、編輯專案中的檔案，理解跨檔案的邏輯關係。

執行指令

可執行測試、建置、安裝套件等 shell 指令，並根據結果自動調整。

Git 整合

協助撰寫 commit、開 PR、檢視 diff，遵循專案既有的提交風格。

子代理與技能

可呼叫專門的 Subagent 處理探索、審查等任務，或使用自訂 Skill 執行固定流程。

Plan Mode

先規劃再執行，複雜任務可先產出計畫供你確認後再動手實作。

MCP 擴充

透過 Model Context Protocol 連接外部工具，如資料庫、瀏覽器、第三方服務。

.claude/settings.json 詳解：如何減少授權跳出視窗

Claude Code 預設對「有風險的動作」（執行 shell 指令、編輯檔案、存取網路等）都會跳出確認視窗。 這是安全設計，但如果每次都要手動點「允許」，體驗會很卡。settings.json 讓你把 「已經確認安全、常用的動作」預先加入允許清單，之後就不會再跳出詢問。

設定檔放在哪裡？（優先順序由高到低）

檔案位置作用範圍建議用途
~/.claude/settings.json個人全域設定你自己在所有專案都通用的允許清單
.claude/settings.json專案共用設定建議提交進 git，讓整個團隊共享同一套規則
.claude/settings.local.json專案個人設定只給你自己用，通常加進 .gitignore，不提交
💡 更精確的名詞是「權限規則的合併」而非單純覆蓋：不同層級的 allow / deny / ask 清單會合併生效，deny 的優先權高於 allow。若組織有設定「企業層級管理政策」，那一層的規則優先權最高，個人設定無法覆蓋。

基本結構

{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Bash(npm run lint)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Bash(git log:*)",
      "Read(~/.zshrc)"
    ],
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(git push --force:*)"
    ],
    "ask": [
      "Bash(npm publish:*)"
    ]
  },
  "defaultMode": "default"
}

規則語法是 工具名稱(細節條件)：

  • allow：符合的動作直接放行，不再詢問
  • deny：符合的動作永遠拒絕，優先權最高（即使 allow 裡也有寫，deny 仍會擋下）
  • ask：即使有更寬鬆的 allow 規則，符合這裡的仍會強制詢問（適合「大部分允許，但這個例外要小心」的情境）
  • Bash 規則可用 :* 當作字首萬用字元，例如 Bash(npm run test:*) 會允許 npm run test、npm run test:unit 等所有以此開頭的指令
  • Read / Edit / Write 規則可用檔案路徑或 glob，例如 Edit(src/**) 只允許編輯 src 目錄內的檔案

減少授權跳出視窗的實用做法

1. 允許唯讀 / 無風險指令

把 git status、git diff:*、git log:*、ls、cat、grep 這類不會修改任何東西的指令加入 allow，是最安全也最有感的第一步。

2. 針對專案常用指令加白名單

例如 Bash(npm run test:*)、Bash(npm run build)、Bash(pytest:*)，把你天天在用、確定安全的指令加進去。

3. 用 /permissions 互動式管理

在對話中輸入 /permissions 可以直接檢視、新增、刪除目前的權限規則，不用手動編輯 JSON。

4. 用 fewer-permission-prompts 技能自動產生

這是內建的 Skill，會掃描你近期的對話紀錄，找出你「已經常常手動允許」的唯讀指令，自動幫你整理成建議的 allowlist 加進 .claude/settings.json。

5. 謹慎使用 defaultMode

"defaultMode": "acceptEdits" 會自動接受檔案編輯類動作，適合你已經很信任的專案；但危險操作（強制推送、刪除、bypass 所有權限）不建議整批放行，寧可用明確的 allow 清單逐項加。

6. deny 擋住高風險指令

即使你把整體模式放寬，也建議明確 deny 掉 rm -rf、git push --force、git reset --hard 這類不可逆操作，多一層保險。

⚠️ 提醒：allowlist 是「你確定安全才加」的清單，不是越多越好。像 curl、rm、 涉及金鑰 / 憑證的指令，建議保留詢問，避免 Claude Code 在你沒注意時執行到非預期的高風險操作。

詳細使用情境與範例

以下整理 8 種常見的實際使用情境，每種都附上可以直接照抄修改的提示詞範例。

1. 除錯 2. 重構程式碼 3. 補齊測試 4. Code Review 5. 撰寫文件 6. 熟悉陌生專案 7. Git 與 PR 流程 8. 大型跨檔案變更

1除錯（Bug Fixing）

描述症狀（錯誤訊息、重現步驟）比直接說「這裡壞了」更有效，Claude Code 會自動搜尋相關檔案、加上除錯輸出、執行測試驗證。

> 使用者回報登入後偶爾會被導回登入頁，錯誤log是
  "TokenExpiredError: jwt expired"，
  幫我找出原因並修正

> 執行 npm test 後 auth.test.js 有 3 個失敗，
  幫我逐一排查並修好，改完後重新跑一次測試確認

2重構程式碼

可以指定重構範圍與目標（可讀性、效能、拆分職責），Claude Code 會先說明計畫再動手，避免大範圍破壞性修改。

> UserService.ts 裡的 processOrder 函式有 200 多行，
  幫我拆成幾個職責單一的小函式，行為要完全不變

> 把這個專案裡重複出現的 fetch + try/catch 邏輯
  抽成一個共用的 apiClient，並套用到所有呼叫的地方

3補齊測試

可以請它先分析覆蓋率缺口，再針對邊界案例（空值、例外、併發）補測試，而不只是測 happy path。

> 幫我找出 src/utils 裡沒有單元測試的函式，
  列出清單後依優先順序幫我補上測試

> 幫 PaymentValidator 補上測試，特別涵蓋
  金額為 0、負數、超過上限、幣別不合法這幾種邊界情況

4Code Review / 安全性檢查

在合併前讓 Claude Code 幫忙看一次 diff，抓邏輯錯誤、資源洩漏、或 OWASP Top 10 類型的安全性問題。

> 幫我 review 目前這個分支和 main 的差異，
  找出可能的 bug 或可以簡化的地方

> 檢查這次改動有沒有 SQL injection 或
  XSS 風險，特別是有拼接使用者輸入的地方

5撰寫文件

可以請它依照程式碼實際行為產生文件，而不是憑空捏造，並保持與現有文件風格一致。

> 幫這個專案寫一份 README，
  說明安裝方式、環境變數設定、和啟動指令

> 幫 src/api/*.ts 裡所有 exported 函式
  補上 JSDoc 註解，說明參數與回傳值

6熟悉陌生專案（Onboarding）

接手一個不熟悉的大型專案時，可以請它先幫忙畫出架構全貌，再逐步深入特定模組。

> 我剛加入這個專案，幫我快速說明整體架構、
  主要模組分工、以及資料是怎麼從前端流到資料庫的

> 這個專案的付款流程程式碼在哪裡？
  幫我整理呼叫順序和涉及的檔案清單

7Git 與 PR 流程

Claude Code 會參考專案既有的 commit 風格撰寫訊息，也能協助處理 merge conflict。

> 幫我把目前的改動分成兩個邏輯清楚的 commit，
  一個是重構、一個是新功能

> 幫我建立一個 PR，標題和描述要說明
  這次改了什麼、為什麼改、以及怎麼測試

8大型跨檔案變更（遷移、升級）

面對牽涉數十個檔案的變更（例如升級套件版本、更換 API），建議先讓它進入 Plan Mode 產出計畫，確認範圍後再執行，避免改壞不相關的地方。

> 我們要把整個專案從 Moment.js 換成 date-fns，
  先幫我列出所有用到 Moment 的地方和影響範圍，
  規劃好之後再開始改

> 把所有 class component 改寫成 function component
  加 hooks，一個檔案一個檔案做，每改完一個就跑一次測試

使用建議

  • 在專案根目錄放置 CLAUDE.md，說明專案慣例、架構與注意事項，Claude Code 會自動參考。
  • 對於有風險的操作（如刪除檔案、強制推送），Claude Code 會先詢問確認再執行。
  • 複雜任務建議先讓它進入 Plan Mode 產出計畫，確認方向無誤後再執行。
  • 可透過 .claude/settings.json 客製化權限與行為。
  • 對話太長時可用 /compact 或 /clear，避免上下文過度膨脹影響回應品質。
